## Required tooling (MCP)

Always use these two MCP servers in this repository:

- **CodeGraph** (`.codegraph/` is present at the repo root). Before grep, find or reading files to understand or locate code, call `codegraph_explore` (or `codegraph explore "<symbols or question>"` in the shell). Name the symbols or files in the query. It returns their current line-numbered source, the call paths between them and what depends on them, so treat it as a Read you've already done and edit from it. Don't re-verify its results with grep. If a response carries a staleness banner, Read only the files it lists. Use plain Read/Grep for what it doesn't index (configs, CSS, docs).
- **Context7** (`resolve-library-id`, then `query-docs`). Use it for current documentation whenever a task involves a library, framework, SDK or CLI tool. In this repo that means React 19, Vite 6, Vitest 5, `@vitejs/plugin-react`, ESLint 9 flat config and its plugins, Tailwind CSS 4 and `gh-pages`. Do it even when you think you know the answer, because training data may be outdated. Pass the full question to `query-docs`, and use a version-specific library ID when the version matters. Skip it for refactoring, business-logic debugging and general programming concepts.

npm run preview    # serve the built dist/

npx vitest run src/suprematism/validate.test.js   # one file
npx vitest run -t "reports MARGIN"                # tests whose name matches (regex)

`npm run deploy` builds twice: npm runs `predeploy` (`npm run build`) automatically, and `deploy` itself starts with `vite build`.

Tests live next to the code as `src/**/*.test.js` and run in Node (see [vitest.config.js](vitest.config.js), which deliberately replaces `vite.config.js` for tests). Import `describe`/`it`/`expect` from `'vitest'`; ESLint runs on tests with browser globals only, so don't use `process` or `Buffer`.

## Architecture

Supremath is a single-page React 19 + Vite app (plain JS/JSX, no TypeScript) that generates a random Suprematism-style composition as full-screen SVG. It has no backend, router or state library. The deployed site is https://supremath.art (`base: '/'` in [vite.config.js](vite.config.js)).

The work is split in two:

- **The generator**, [src/suprematism/](src/suprematism/): pure JS, no React, deterministic given an `rng`. It decides what a composition looks like and proves it follows the laws.
- **The UI**, [src/App.jsx](src/App.jsx) (mounted by [src/main.jsx](src/main.jsx) inside `StrictMode`) and [src/ShapeView.jsx](src/ShapeView.jsx): buttons, About modal, animation loop, export. It never builds shapes itself.

### The generator and its "laws"

`generateComposition({ width, height, rng = Math.random, mode })` in [generate.js](src/suprematism/generate.js) returns `{ mode, width, height, shapes, meta }`. With no `mode` it picks `dynamic` (80%) or `static` (20%), two orders Malevich names. The loop is **build, validate, retry, fall back**:

1. Up to 60 attempts of the mode's builder ([dynamic.js](src/suprematism/dynamic.js) or [static.js](src/suprematism/static.js)). A builder returns shapes or `null` and leaves the reason in `build.lastFailure`.
2. Dynamic only: 100 attempts of the conservative profile, then 20 attempts of `static`.
3. [fallback.js](src/suprematism/fallback.js) `minimalStatic`: a black square with a small red satellite, valid by construction. `meta.fallback` says which tier was used and `meta.rejections` counts why attempts failed. A healthy generator needs about 1.8 attempts and never reaches tier 3; the tests assert this so the chain can't hide a weak builder.

**There are always at least two forms** (`LIMITS.counts`: dynamic 5-9, static 2-3). Static layouts are a main form plus one or two satellites; a lone "Black Square" is not generated.

What counts as "valid" is [validate.js](src/suprematism/validate.js):

- **`LIMITS` are the laws** (about 35 rules, each with a code in `VIOLATION_CODES`): flat palette colours only, white ground, hierarchy (one dominant form), a shared tilt with a few free accents, asymmetric balance by visual weight, lighter forms above heavier ones, irregular rhythm, margins, no near-miss gaps, crossings of different colours, and so on. The thresholds are our own formalisation of museum and academic descriptions of Suprematism (Malevich's primary texts could not be consulted), so change them knowingly.
- **`PARAMS` are where the generator aims**, mostly well inside the laws (`params.test.js` checks they are nested). A composition is only returned once `validateComposition` accepts it. The laws hold for the composition *as generated*; the animation deliberately does not keep them (see below).
- **The long line**: a dynamic composition (6-9 forms) gets one very long, very thin line with `PARAMS.dynamic.longLine.chance` (0.4, so about 35% of them). It is one of the forms, not an extra: the others (at least five) are built as usual, and `addLongLine` in [dynamic.js](src/suprematism/dynamic.js) lays the line across the finished composition **by trial**. Each candidate (angle along the main tilt or square to it, length a share of the longest line that fits the margin at that angle, position, colour from those already in use) is put to `validateComposition` with every other form, and the first one the laws accept is kept; half of the lines must cross another form. When none fits the composition goes without it, so the line can never make an attempt fail. It is not part of the area ladder (which would make it short) and not part of `fitToStage` (which would shrink every other form to fit it). The law side: a bar's aspect may now reach `LIMITS.barAspect` (3-160), and `LONG_LINE` allows at most `vocabulary.veryLongMax` (1) bars longer than `veryLongAspect` (40) in a dynamic composition and none in a static one. Measured on 8 viewports: the line is 0.9 `U` long in the median (the longest ordinary line was about 0.5 `U`), up to about 1.4 `U`, aspect about 60 (never above 140), and attempts per composition stay about 1.8. The conservative profile and the static mode never get one. It changed what every seed generates, which is the case that `GENERATOR_VERSION` exists for (see "Generator version" below).
- **Adding a rule**: add its code to `VIOLATION_CODES` and a mutator for it in [testUtils.js](src/suprematism/testUtils.js). `validate.test.js` fails if a code has no mutator, so no rule can ship untested.

Other modules: [geometry.js](src/suprematism/geometry.js) (centre-based shapes, the "stage", polygon distance and overlap; crosses are split into disjoint convex pieces), [weight.js](src/suprematism/weight.js) (visual weight and balance, shared by generator and validator, so it has hand-computed tests), [palettes.js](src/suprematism/palettes.js) (`GROUND_COLOR`, pure colours, palettes), [random.js](src/suprematism/random.js) (`createRng(seed)` and sampling helpers), [animation.js](src/suprematism/animation.js), [transition.js](src/suprematism/transition.js), [order.js](src/suprematism/order.js), [version.js](src/suprematism/version.js) (`GENERATOR_VERSION`), [index.js](src/suprematism/index.js) (public API).

Shape model: `{ id, type, cx, cy, w, h, rotation, color, role }` with `type` one of `square | bar | circle | cross | triangle`, rotation in degrees about the centre. A thin line is just a bar. The "stage" is the centred part of the window whose aspect ratio is clamped to 0.4–2.5, and every threshold is relative to `U = min(stage width, height)`. The minimum supported window side is 240 px.

### Generator version

A link names a picture by its seed and canvas size, and the generator **recomputes** the picture, so a link brings the same picture back only from the same generator. [version.js](src/suprematism/version.js) holds `GENERATOR_VERSION` (now 1), every link carries it (`#seed=483920&size=1920x1080&v=1`), and a link made by another version is recognised (`madeByAnotherGenerator` in [permalink.js](src/permalink.js)): the app builds the picture with the generator it has, rewrites the address to name that picture (so a re-shared link is truthful) and says once that the picture may differ. A link with no version, or a garbled one, is not accused: it is taken as typed by hand. The version does not bring the old picture back; it only makes the failure honest instead of silent.

**Raise `GENERATOR_VERSION` whenever what a seed produces changes**: a law, a parameter, a new kind of form, a reordered random draw, even a bug fix that moves a form. `generator.version.test.js` is the reminder. It keeps one fingerprint per canvas (4 canvases, seeds 1 to 300, in [fingerprints.js](src/suprematism/fingerprints.js)), fails when the output no longer matches, and prints the whole new `fingerprints.js` to paste in, with the next version number; the version and the table are raised together, and the test fails if they disagree. It notices a change that touches about 1% of the compositions or more (a long-line chance of 0.40 raised to 0.41 is caught); a change that touches one composition in a thousand slips past it, and breaks one link in a thousand.

### Animation ("entropy")

[animation.js](src/suprematism/animation.js): `createMotion(comp, rng)` gives **every form its own random speed, direction and spin**: each form drifts in a straight line (`MOTION.speed`, 0.125-0.325% of `U` per second, about 1.4-3.5 px/s on a 1080p screen) and every form that can turn does so at its own rate (`MOTION.spin`, 1-2 degrees per second, either way round). The circle never turns, and nor does a form whose circumscribed circle does not fit inside the window (`canTurn`): a very long line would leave the window as it came round to vertical, so it keeps its angle and still drifts and bounces. Nothing steers the forms back, so the composition gradually comes apart; that is the intended entropy. The one exception is `motion.restore()` (the "Restore order" button): every form glides back to its generated place in its own time (`MOTION.restore`, 3-5 s, eased, turning the short way round for its symmetry), those that arrive first wait, and when the last one is home the composition is exactly as generated again and everything drifts off on fresh random courses (`motion.restoring` is true meanwhile; a second call is ignored). A paused animation resumes when the button is pressed. Forms bounce off the edge of the window and never leave it (`bounce` also handles a form that turns into a wall). `motion.step(dt)` advances the state and `motion.shapes` is the current picture.

**Transition between compositions:** [transition.js](src/suprematism/transition.js) `createTransition(from, to)` is what Regenerate (and a resize, or a pasted link) plays instead of a cut: the forms on screen shrink away, smallest first, and the new composition's forms grow in, the dominant one first and the accents last, each turning at most `TRANSITION.spin` (18 degrees) as it settles; about a second in all (`transition.duration`). Forms only change size and turn, never colour or opacity, so every frame is made of pure flat colours (blending red into blue would give muddy purples, which are not in the palette). Like the motion it is just a list of shapes over time (`shapes`, with `done` and `step(dt)`): leaving shapes get ids `gone0, gone1, ...`, arriving ones keep their own, and `shapes` equals `to` exactly when `done`. `from` may be the middle of an earlier transition, so pressing Regenerate again interrupts without a jump. Nothing in a transition is checked against the laws.

The laws in `validate.js` are therefore **not** kept while the animation runs, and nothing tests that they are. What *is* measured is how far they have drifted: `measureOrder(comp)` in [order.js](src/suprematism/order.js) runs the validator and returns `{ order (0..1), kept, total, broken }`, counting only the **laws of place** (position, turn, distance; `LAWS_OF_PLACE`, per mode). Laws about what the forms are (count, colour, size; `LAWS_OF_KIND`) can't change under motion and would only pad the number. **A new violation code must be added to one of these lists**: `order.test.js` fails otherwise. Measured on 40 seeds at 1080p, dynamic order falls from 100% to about 74% in 15 s and then flattens near 63%; static falls to about 40%. Speeds and spins are the knobs if the movement feels too fast or too slow. Time comes from the frame timestamps through `createClock` (`clock.delta` is the last step), so speed doesn't depend on the refresh rate and pausing doesn't make the picture jump.

### Tests

- Reference compositions `goodDynamic()` / `goodStatic()` in `testUtils.js` are built by hand, independent of the generator, and must stay valid.
- `generate.*.test.js` run `runBatch` (seeds 0..N per viewport and mode, 16 viewports from 240x240 to 5120x1440) and assert zero violations; N is 500 by default, `VITE_PROP_SEEDS` overrides it.
- `longLine.test.js` checks the long line (a share of compositions at every viewport, length and aspect within the parameters, one at most, never static or conservative, tilt shared, many cross something, no extra work for the generator); `params.test.js` keeps its parameters inside the laws.
- `animation.test.js` checks that every form gets its own speed, direction and spin inside the gentle ranges, that circles and forms that cannot turn never do, the wall bounce, smoothness, determinism per seed, and that forms stay in the window over six simulated minutes at every viewport.
- `generator.version.test.js` keeps the fingerprints of what the generator makes (see "Generator version") and tests the fingerprint itself; it generates 1200 compositions, a few seconds.
- `transition.test.js` checks the first frame is the picture on screen and the last is the new composition exactly, that forms only shrink going out and grow coming in, the order they come and go, flat colours, unique ids, interruption without a jump, and (with a mutation-checked guard) that no form leaves the window during a transition.
- When a property test fails, it prints the seed and violation codes; rerun that seed through `generateComposition` to reproduce.
- **Checking animation timing in a real browser:** an automated or occluded Chrome may run `requestAnimationFrame` at about 3 fps, and `MOTION.maxDt` (0.1 s) then makes every animation run about three times slower than real time (check with a one-second rAF counter before trusting a measured duration). Replace `requestAnimationFrame` with a timer to test: `window.requestAnimationFrame = (cb) => 1e9 + setTimeout(() => cb(performance.now()), 16)` and make `cancelAnimationFrame` clear it (`id >= 1e9 ? clearTimeout(id - 1e9) : real(id)`). Without the matching cancel the loop that the app thinks it stopped keeps running, and pause appears broken.

### The UI (App.jsx)

- **Render model:** `sceneRef` holds the current composition (`comp`, as generated) and its `motion`; `shapesRef` holds the forms as they are drawn right now (`motion.shapes`). Anything that changes `shapesRef` must be followed by `setVersion(v => v + 1)`. `sceneRef` is initialised lazily on the first render (a `useRef(generate())` would regenerate on every render). `showScene(request)` is the one place that puts a composition on screen (see "Seed and link"), and it starts a transition from the forms drawn right now (`shapesRef.current`) unless `prefers-reduced-motion` is set. While `scene.transition` is set the loop steps it instead of the motion (the motion has not started, so the forms land exactly as generated), does not measure order (the meter reads the new composition's 100%), and runs even when the entropy is paused, because `transitioning` is state that the loop effect depends on; when the transition is `done` it hands over to `motion.shapes`. During a transition Restore is disabled, and the export handlers wait (`settled`) so that a PNG, SVG or share never catches the forms half-way. Regenerating also resets the clock. The scene also carries `order` (a `measureOrder` result) and `orderAt` (the animation time it was taken); the loop refreshes it every `ORDER_INTERVAL_S` and [OrderMeter.jsx](src/OrderMeter.jsx) (top-left, click to list the broken laws) shows it. The meter is HTML, not part of the SVG, so it is not in exported PNGs.
- **SVG:** the `viewBox` comes from the composition (`comp.width` x `comp.height`), not from the window, so a composition scales to fit while a resize is being debounced. [ShapeView.jsx](src/ShapeView.jsx) draws each shape in its own local coordinates inside `translate(cx cy) rotate(r)`.
- **Poster caption:** [Caption.jsx](src/Caption.jsx) draws "SUPREMATH № <seed>" and `supremath.art` in the top-right corner, as the **last** child of the `<svg>`, so it lies *over* the forms and is always readable, and it is in every export (PNG, SVG, the image Share sends). It is part of the picture, not an overlay. Each line is drawn twice: first a copy outlined in the ground colour (the halo, `haloWidth`, at least 1.5 px outside the letters; `aria-hidden`), then the letters on top. That is what lets it read on a black, blue, red or yellow form as well as on the ground, where the halo is invisible. It is two copies and not `paint-order`, which vector editors ignore. Its position and size come from `captionLayout` in [caption.js](src/caption.js), in viewBox units: it scales with `U` like the forms but never below 10.5 px, and it is flat (solid fills, system fonts, so an exported file looks the same everywhere). It shares the top edge with the order meter, so the meter shrinks to 6.5 rem at 400 px and below to keep clear of it; a six-digit seed fits from about 280 px wide. Change the caption text or size and re-measure the gap at 320, 360 and 390 px.
- **Seed and link:** a composition is named by `seed` and the `width` x `height` it was built for (the generator is deterministic in both; `buildScene` uses `createRng(seed)`; the motion still uses `Math.random`). [permalink.js](src/permalink.js) writes and parses the hash, `#seed=483920&size=1920x1080&v=1` (`v` is the generator version, see "Generator version"; a scene made from a link from another version is `staleLink` and the app says so with a longer notice); parsing is strict and returns null for anything unusable (a bad size is dropped, a bad seed rejects the whole hash). `showScene(request)` is the one place that builds a scene, resets the clock and writes the address with `replaceState`, so the address always names the picture on screen (and a refresh brings the same composition back; Regenerate gives a new one). A `hashchange` (a link pasted into the open tab) shows what it names. A scene made from a link with a size is `pinned`: a window resize scales it to fit (the `viewBox` does that) instead of regenerating it, so a shared picture survives a phone's address bar collapsing. A hash with only a seed is built for the current window and is not pinned. Regenerate, or any resize after it, is back to normal.
- **Resize:** debounced by 250 ms. `showAboutRef` mirrors `showAbout`; a resize while the About modal is open is remembered (`pendingRegenRef`) and applied when it closes. Pinned scenes ignore resizes.
- **Export / share:** [exportPicture.js](src/exportPicture.js) copies the live `svg.fullscreen-canvas` (the class is load-bearing) into a standalone document, because the on-screen element is sized in `vw`/`vh` and its ground is a CSS background, neither of which survives in a file: it gets the composition's own width and height, no `style` or `class`, and a ground-coloured `<rect>` first. `svgBlob()` is the .svg download; `pngBlob()` draws the same document through an `Image` and `<canvas>` at 300 DPI (viewBox size x 300/96) and was checked pixel for pixel against the old inline pipeline. Both export what is on screen right now (the drifted picture), while the link brings back the composition as generated. Share sends the PNG together with `title` and `url` where `navigator.canShare` allows files, only title and url where it does not, and where there is no `navigator.share` at all (most desktops) it copies the link and shows a notice; it never calls `alert()`, which blocks browser automation. The notice is the `.notice` element driven by `showNotice`.
- **UI:** the floating buttons (about, pause/play entropy, restore order, regenerate, download, share) sit in the `.floating-buttons` bar. Download opens a small PNG / SVG menu above it (`.download-menu`, state `downloadOpen`; it closes on a choice, on a press anywhere else, on Escape, and when About opens), so a new export format costs a menu item, not a button. The menu items are `<button>`s inside the bar, so their CSS must repeat `all: unset` under `.floating-buttons`, which styles every button in it as a white circle. When the About modal opens they slide toward the center via the `slide-*` CSS classes, and a separate close button appears. The bar overlays the bottom of the canvas and the generator does not avoid it, so a form can sit under a button. All icons are inline SVG, and the About text and social links are hardcoded in JSX. The About text describes the product (numbered compositions and links, the order meter, Restore, PNG/SVG export, and that the rules are the author's own reading of Suprematism, not Malevich's): keep it in step when those change, and note that "keep the link and it comes back" holds for the same `GENERATOR_VERSION`: a link from another version gets a notice, not the old picture. At 520 px and below the About text is smaller and its box is as tall as the room above the close button allows, so that the links under it are not cut off (check it at 360x740 and 375x667 after changing the text). The social links carry `aria-label`s, since they are icon-only. Six buttons need about 510 px; at 520 px and below the bar is scaled with `zoom: 0.7` (icons included, buttons stay about 45 px) and still fits one row at 320 px, with `flex-wrap` only as a safety net, so no button is ever cut off. Check the bar at 320, 360 and 390 px whenever a button is added.

## Styling gotchas

- **Tailwind is not actually wired up.** `tailwindcss` is in `package.json`, but there is no Vite plugin, PostCSS config or `@import "tailwindcss"` anywhere. The utility classes in `App.jsx` (`absolute`, `w-screen`, `flex`, `gap-2`, `bg-black`, …) currently do nothing. The real styling comes from the hand-written rules in [src/index.css](src/index.css) plus inline styles. To use Tailwind, add `@tailwindcss/vite` and `@import "tailwindcss"` first.
- [src/App.css](src/App.css) is leftover Vite-template CSS that nothing imports. Edit [src/index.css](src/index.css) instead.
- `index.css` also keeps the default Vite template's global `button`, `a` and `h1` styles. The floating buttons override them with `all: unset`.
- The ground colour `#f2f2f2` is `GROUND_COLOR` in [palettes.js](src/suprematism/palettes.js) and is duplicated in `index.css` (the `html, body` rule and the `svg.fullscreen-canvas` rule), so change all three together.
- The About modal's social links use `class=` instead of `className=` (React tolerates it, with a console warning). Their SVGs use hyphenated attributes like `fill-rule`.
- The "Loved by the King" Google Font is loaded in [index.html](index.html) but is not referenced by any CSS rule.

## Lint

[eslint.config.js](eslint.config.js) is a flat config using `@eslint/js` recommended, `react-hooks` and `react-refresh`. `no-unused-vars` ignores identifiers starting with an uppercase letter or `_`, which is why a component or constant can go unused without an error.
